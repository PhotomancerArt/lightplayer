Device card · firmware versions and update states

Thesis. Once boards update over Bluetooth and Wi-Fi, the firmware zone has thirteen things to say instead of two. They sort into three kinds: progress (something is happening, nobody needs to act), needs you (nothing moves until a person does something), and information (true and worth knowing, nothing to do). A person should tell the kind at a glance, read the version as a version (2026.10.03-1, not fw-esp32c6 a41c9e2), and never meet a confirm dialog: an update is one button, and putting a board's firmware back is no button at all.

Deliberately light. The card's four zones and fixed rows stay exactly as they are; a device-pane rework comes later. Every concept below fits inside today's rows except D, which adds one 17 px line. Sample board: Porch lights, a XIAO ESP32-C6 on 2026.10.03-1; this Studio carries 2026.10.05-2.

3The version, read as a version

The header's second identity row and the firmware line, for every way a board and this Studio can compare. The version leads; the commit is detail (dim, and in full on hover and in the terminal). "Out of date" only ever means an older version. A dev build compares by commit, and only when neither side is a release. The modified-tree suffix (-dirty-142233PT) reads as "(modified)", with the raw string on hover.

4The editor's device popover

The other place a board's state is shown: the header's device segment while the editor is open on it. Its run word takes the same short words, and its stat line the version. Nothing else changes there.

5What the board's own lights show

During an update the show stops and the strip shows one solid colour, no animation, so a dark porch still says "alive". Two colours only. Concept C draws the same colour in the card's picture slot, so the card and the porch agree.

Dark yellow: updating. Firmware is being written, finished or put back. Leave it powered; if it stops, any Studio picks it up again.
Dark red: waiting for its firmware. Part of its firmware is missing and no Studio has put it back yet. Connecting any Studio that has that version fixes it with no click.

6The buttons as offers

Every button above is an offer built in core, so the app agent sees and presses the same ones. "Studio does it" rows are not offers at all: finishing an interrupted update and putting missing firmware back happen on connect, with no click. Level is what pressing costs: R Routine (plain; the agent presses it), U Undoable (error tint, one click), L Lasting (error tint, two-click arm; the agent hands it to you).

One ruling to make: is an over-the-air update Routine or Lasting? Today "Update firmware" is Lasting (it is the USB flash, and the copy says "Replace what this board runs?"). An over-the-air update is different: Studio holds a backup of the current firmware before writing a byte, a failed update rolls back by itself, and the project stays. Nothing is lost, so the honest level is Routine: one plain button, no error tint, no arm. The cost: the app agent may then update a board when asked, without handing the button to you. Lean: Routine for Update, Reinstall, Try again and installing this Studio's version; Lasting only for "Other version…" when the chosen version is older (an older build may not read the board's project), and for the USB flash and Factory reset as today.
