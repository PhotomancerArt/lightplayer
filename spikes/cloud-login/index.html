Cloud login & account — design spike

The lp-cloud service is live and already speaks auth (/auth/google, hashed-token sessions, logout); the Studio frontend has no login UI at all. This spike explores the whole account surface: the signed-out affordance in the chrome, the signed-in identity dropdown, a minimal profile page (avatar + given/family names — nothing more), and a multi-account variant to pressure-test the architecture. Ambient constraint from the cloud vision (D20): viewers never need an account — a share link opens running with zero login, so the chrome must never nag the anonymous 95%. Avatars here are generated stand-ins; the real one is Google's profile photo (currently discarded at the OAuth callback).

Converged 2026-08-07 — gate rulings: §1 A (quiet text link; C's inline ask composes), §2 A growing into C, §3 B structure with A's content, §5 lean switch model, bones only. New ruling folded in: auth stays provider-based — Google is prod config, not the architecture; §4 shows the same "Sign in" on three deployments (shape borrowed from skybridge's auth-connections model). Rejected concepts shrink to strips.

4 · One “Sign in”, many providers — the surface is server-defined

Ruling: don’t lock into Google. The shape (after skybridge’s auth-connections model): the server exposes a public login-options call — which connections this deployment has (oidc rows like Google, or a local connection whose methods are pick-a-profile, password, …) — and the client renders sign-in from that answer. Google is a config row, not a code path; password is a method of local, not a provider sibling. Below: the same “Sign in” click on three deployments. The dev picker is LightPlayer’s existing /auth/dev grown up — and it stays triple-gated (build config + server config + route re-check), never compiled into prod.

5 · Multi-account — try it, and what it costs

Live demo: click the avatar, switch accounts, watch the chrome follow. Below it, the three ways to build switching — the spike’s architectural point is that the cheap one is genuinely good, because the provider’s own picker (Google already forces prompt=select_account; the dev picker is one) does the heavy lifting, and the dropdown’s account list is just local memory of past sign-ins, not server state. Ruling: bones only — ship the shape, don’t smooth the edges.

Switch = re-auth through the provider lean · ship this

One active session, exactly today’s server. “Switch” and “Add account” re-enter the sign-in flow (/auth/google?next=… in prod — Google’s picker, no password re-entry; the profile picker in dev) and the new session replaces the cookie. The dropdown’s account rows are a client-side memory of past sign-ins (name, email, avatar, provider in localStorage) — sugar, not server state.

Cost: a page round-trip per switch (~1–2 s). Zero new server surface, zero new security model. Multi-account UX exists from day one; the architecture stays one-cookie simple.

Server session-set later · if switching is hot

The cookie names a set of sessions plus an active index; switch = one API call, instant, all tabs follow together. This is Google’s own model minus the /u/0 path hack.

Cost: new session-set store + vocabulary (switch, drop), CSRF thinking on the switch call, and “which account did tab 2 just act as?” questions. Only worth it if switching turns out to be frequent.

Client token vault avoid

Browser holds N bearer tokens (localStorage), sends Authorization headers; per-tab identities become possible.

Cost: tokens leave HttpOnly cookies for script-readable storage (XSS blast radius), the not-yet-built fetch CloudPort grows an auth header path the cookie plane already solves, and OG/share pages can’t see auth. Per-tab identity isn’t worth this.
