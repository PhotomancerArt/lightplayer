Spike · a new board’s setup · round 2

The card’s rows are the setup list

Sean flashed his first board on 2026-10-18 and nothing asked for his Wi‑Fi. Round 1 put four ways to ask beside today’s card. Yona walked a factory-reset board on his desk and set the direction: the rows of the card are actually a great benefit here. its almost a todo list. all we have to do is call out each item.

Decided after round 1 (Yona, 2026-10-19)

  1. Three principles for a new user’s setup. Make it obvious what they need to do. Teach the UI and keep things in place, so setup isn’t a one-off they see once. Minimize decisions, especially repeat decisions.
  2. The rows are the setup list. A row with something to do carries its button (the row action pattern), the way Add project sits on the Project row.
  3. Eight rows: Wi‑Fi, Bluetooth and lightplayer.app get their own, and so does USB. putting it all under the usb feels weird and crowded; separating ble and wifi is normal in settings systems.
  4. lightplayer.app has its own row, for privacy (“lightplayer.app - disabled” is a nice clean thing to say) and for the journey: They see the cloud icon, the name, and an action.
  5. Save everything to the account, with permission. A network set up before is remembered, and the card says so.

The thesis: one card, the same eight rows from a blank chip to a board on the eaves. A row that has something left to do says so and carries its button; a row that is done is one quiet line. The primary is the next thing the board needs, and pressing it opens the row it belongs to, so the setup teaches where each thing lives. The account remembers what you set up once, so the second board needs nothing pressed.

What is true today (checked in the code)

  • Today’s card has five rows, and the Link row holds every link: its details carry the reach facts, the Bluetooth switch, the whole Wi‑Fi panel, link counters and five buttons. On a board with no Wi‑Fi its struck cloud says “lightplayer.app can’t reach it”, which is true and reads as broken.
  • A reinstall or an update keeps the board’s network (the flash never erases the file store). Only Factory reset wipes it; moving Factory reset to the Hardware row is in flight in another session.
  • The board lists the networks it hears (2.4 GHz), keeps up to 8 and joins the strongest, and reports Wrong password, Not in range, No address and Connected, no internet. Studio can read a saved network’s name, never its password.
  • Bluetooth is on and a new board is open: anyone over Bluetooth or on the same Wi‑Fi can edit it. It advertises as LP-3f2a, the digits of lp-3f2a.local. Passwords live in the access panel (Play and Author, each Anyone or Password).
  • The account keeps its key and the play and edit passwords, and Studio puts them on a board at its next USB connect, with no press. Nothing about Wi‑Fi is kept anywhere but the board.
  • lightplayer.app reaches a board that has joined Wi‑Fi, has Cloud relay on (the default) and holds an account key. Sign-in is a page redirect, so it never happens during a flash.

3The rows’ words

Each row in the card’s grammar, icon · kind · name · state · action (docs/ux/anatomy/board-card.md). The four link rows have no kind word: the link’s name is its kind, as the Link row’s is today. The state shows only when it isn’t normal (P4), and a button only when something is left to do.

RowSaysWhen

4The account remembers

Asked once, then never again. The first time a signed-in person adds a network, Remember in your account is on. That switch is the permission. Every board after that joins your remembered networks with no press, and a small account mark at the row’s end says where it came from (hover: “From your account”). The same mark sits on the Access row when the board took your account’s password. Storing a Wi‑Fi password there is a security decision for an ADR in the plan; the precedent is the account’s play and edit passwords, which the service can already read.
