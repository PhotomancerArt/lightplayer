Unified mapping/patching editor shell

G1 ruled: the standalone /patch page is the wrong shell — patching belongs inside the mapping editor, which already has the real selection/tree/canvas architecture. This spike explores the unified shell: project tabs (Nodes · Mapping · Patching), the wiring-order rail grown into a project-scope Fixtures tree (with the channel boxes), a facing Outputs rail (the tree the other way), and one mode switch. The open question is canvas geometry at project scope — three concepts below. Data is the real mini-dome permutation (1,5,4,3,2) plus an unmapped ribbon for the range-grain case.

1 · Concept A — “Atlas”: every fixture in its own map space, tiled

The canvas shows each fixture's own map2d space in a framed tile — the dome's authored geometry, the doors' authored geometry — laid out side by side (auto-packed, not meaningful positions). The unmapped ribbon docks as a range bar: it has lamps but no geometry, and the atlas says so instead of hiding it. Mapping tools operate inside whichever tile the selection lives in. Claim: honest about what a map2d is (per-fixture space), no fake install layout, and the whole project is visible at once.

2 · Concept B — “Focus”: one fixture's space at a time, tree-driven

The canvas is exactly today's editor — one fixture's map full-bleed — and project scope comes from the rails: clicking another fixture in the tree (or the filmstrip, bottom-left) swaps the canvas. The ribbon's “canvas” is an honest range strip. Claim: zero new canvas semantics, mapping tools keep full fidelity, cheapest to build; the cost is that cross-fixture patching is felt through the rails, never seen spatially.

3 · Concept C — “Install”: lamps at output-layout positions

The canvas shows the installed arrangement — lamp dots at the positions the output layout system computed (what the interim /patch page drew, and what the sim shows). Doors sit between the dome sectors they interrupt, because that is where they hang. The ribbon parks in a “no layout” strip. Claim: this is the space a re-plug session happens in — you look at the wall, not at doc coordinates. The cost: it is not the space mapping tools edit in, so mapping mode either switches back to doc space (modal geometry!) or goes read-only here.

4 · Rail anatomy — the two trees and their cells

Shared by every concept. The Fixtures rail is the wiring-order rail grown up: fixture → object → instance, with a channel chip per instance — port hue, port-local lamp range, rotation and reverse markers. The Outputs rail is the same facts inverted: output → port → cells coloured by fixture object, so “what is on IO14” and “where did sector 3 go” are both one glance. Wire annotations are port-named (IO18:1-30) — the D45 replacement for today's per-universe 1:1-23.

Lean: ship B (“Focus”) as the v1 canvas inside the full shell — it is today's editor with project rails, zero new geometry semantics, and everything patching needs is carried by the rails + selection sync. Keep C (“Install”) as the declared follow-up patching-mode view toggle once fixture transforms exist (it is the space a re-plug actually happens in), and treat A (“Atlas”) as the eventual arrange-mode substrate rather than a v1 target. The rails and chips (section 4) are common to all three and can be planned immediately.
