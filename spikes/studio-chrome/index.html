Studio chrome — the IDE workbench (round 1)

The studio editor's chrome, reworked to house advanced editors — starting with Mapping (name ruled). Scope: the editor routes only; galleries and the global site header are untouched. The headline question is the mental ownership model: what owns which panes are visible where, when? Three models are drawn below with the SAME two tenants — the re-housed Nodes card list and the Mapping editor at real density. Use active editor in the strip and watch how each concept reacts: that reaction is the model. Reference: spikes/unified-editor-shell/index.html rounds 1–5 (rails, chips, canvas ratified there).

1 · Today — the scrolling document (for comparison)

Production now: a page that scrolls as a document under the site header. Three columns — project pane · node cards · device card — with fixed identities; on narrow screens they simply stack and you scroll through everything. There is no place to put a viewport-filling canvas, and "which pane is where" is hard-coded per route.

2 · Concept P — “Perspectives” (the view owns everything)

Eclipse's answer. A perspective switch sits above the columns; the active perspective owns the entire arrangement — switching Nodes → Mapping swaps all three columns as one gesture, and Patching is naturally a third perspective. Maximal per-task tailoring; the cost is that the room rearranges itself around you (note the device card simply vanishes outside the Nodes perspective — each perspective shows only what it declared).

3 · Concept D — “Documents” (the shell owns the sides, docs own the center)

VS Code's answer. The center is a document strip — Nodes and Mapping are documents; patching is a mode inside the Mapping document (segmented control in its toolbar). The side columns are shell-owned tool views with their own tabs (left: Project · right: Device / Outputs) that persist across document switches. A document may suggest a side view (opening Mapping reveals Outputs and marks the tab) but never restructures the room. One tree, adorned: the Project tree grows channel chips when the Mapping document is active.

Try the « button in the left column header — columns collapse to a labelled strip, which is how Mapping earns canvas width without a layout change.

4 · Concept S — “Slots” (the shell owns slots, you own the arrangement)

The hybrid. The shell owns three durable slots — [left][main][right] — and views are furniture: stacked, collapsible sections you can move between slots (⠿ grip; try §4 device slot in the strip to put Device on the left). The active document contributes default views — Mapping contributes Outputs, tagged with its origin — and your arrangement outlives document switches. Same document strip as concept D; the difference is entirely in who decides what the sides hold.

5 · Mobile — full-screen main + summon strip

Below the fold breakpoint the workbench is one full-screen main view with a sticky strip: document switch in the middle, summon buttons on the edges. Summoning a side view (☰ project tree · ▤ outputs · ⌁ device) temporarily replaces the main view — a back header returns. This replaces today's stack-and-scroll for the editor routes. The first phone is live — tap its strip. The tablet frame shows the md middle: main + one side column, the other collapsed to a strip.

Concept S (slots) carrying concept D's defaults: the shell owns three durable slots; documents own only the center and contribute side views without restructuring; the user's arrangement is sticky. Perspectives (§2) photograph beautifully but the room rearranging itself is exactly the "two apps" feeling this rework exists to avoid — and it makes the device surface a per-perspective decision, which is how panes get lost.
