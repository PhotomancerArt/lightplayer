Wi‑Fi on a board — set up and manage

Yona (2026-10-04, on #972): “Ideally the board can know about more than one SSID, and it should be easy to be adding one, and ensure that it actually works. ‘Join this network’ is a weird option.” And: “It probably starts not set up … if we can get the SSID of the current network from the computer or phone, we should. If we can get the list of nearby SSIDs from the board with signal power, we should. Once you select a network, get the password and verify that we can connect. … I have Starlink in my truck, at my house, and at my apartment. They’re all different. It would be great if it just worked. Make it as easy as possible. Bigger picture: saving the Wi‑Fi details to the user’s account.”

The thesis: Wi‑Fi is a short list of places, not one setting. A board keeps several networks and joins the strongest one it can hear — your truck, your house, your apartment — with no order to manage. Adding one is picking from what the board hears (strongest first; ones your account already knows are marked, and need no typing), then the board actually tries it — found · password accepted · got an address · reached lightplayer.app — and keeps it only when it works. A network that isn’t in range (setting up the truck from the house) is saved for later on purpose. The confusing “Join this network” switch goes; what’s left is one Wi‑Fi switch for the whole board and one Cloud relay switch, both on by default.

What a web page can’t do: no browser tells a page the name of the Wi‑Fi the computer or phone is on — Chrome, Safari and Bluefy have no API for it (Android Chrome’s Network Information API says “wifi”, never which). So “use the network I’m on” comes from two places that work: the board’s own scan (it’s in the same room — its strongest network is almost always yours), and your account (a network you set up once is marked everywhere after). lp-cli or a native app could read the SSID; Studio can’t. The C6 hears 2.4 GHz only, so a “-5G” network never appears — the copy says so where it matters.
Needs firmware the board doesn’t have yet: today’s image stores a network but can’t scan or join (roadmap M6). Every concept degrades honestly — set Firmware → stores only in the strip: no scan (type a name), no test (saved, “joins after a firmware update”). #972 is unmerged, so /.lp/network.json can still change shape at version: 1 with no migration — section 5.

2“Make sure it actually works” — the test join

One checklist, used by every concept. The board tries the network before it keeps it; each step names what failed in words a person can act on. The last step only shows while the cloud relay is on. Over Bluetooth the board keeps talking while it tries (the C6 shares its radio between the two).

4Your account remembers networks — where the password lives

The payoff is the second board, and the truck: one press puts every network you’ve used onto a new board. The question is how the cloud holds a house’s Wi‑Fi password. Precedent: the account’s Play/Author passwords are already stored readable by the service (easy-access ADR, D7) — “shareable passwords, like a Wi‑Fi password”.

4AIn the account, like its passwords

Stored with the account record, encrypted at rest with the service’s key; any browser signed in as you gets them, cached for a phone at camp with no internet. Each network you add is remembered unless you untick it; Settings lists them with remove.
  • Same trust as the account passwords already there; one more table, no new crypto.
  • Works on a brand-new browser and on Bluefy.
  • The service (and anyone who breaks into it) can read your house Wi‑Fi password.

4BSealed to your devices

The cloud holds only ciphertext. The key comes from a passkey (WebAuthn PRF) or from a browser that already has it (handed over by QR/USB).
  • The service can’t read them.
  • Sign-in is Google/GitHub today — no passkey to derive from; a new browser needs a ceremony before it sees your networks.
  • Lost every key = networks gone (fine — retype them).

4CThis browser only

Remembered in the browser (like the remembered access passwords), never uploaded.
  • Nothing new in the cloud.
  • The phone you set the truck up from doesn’t know the house; the payoff mostly goes away.

4DAsk the board you already have

A board never gives a password back over the link (write-only, #972) — so “copy Wi‑Fi from my other board” would need the boards to hand it over between themselves (ESP-NOW/BLE, sealed). Not proposed; listed because it’s the obvious ask and the answer is no.

5What the board holds and says, for the lean

To reshape #972 before it merges (still version: 1, no migration). Green = new against #972.

// /.lp/network.json — write-only on every link (unchanged rule), plaintext at rest (unchanged, WQ2)
{
  "version": 1,
  "wifi": true,                  // the board-level switch ("Wi‑Fi"), replaces each network's "enabled"
  "cloudRelay": true,
  "networks": [                  // replaces the single "wifi" object; at most 8; order = when added
    { "ssid": "Starlink Home",  "password": "…" },
    { "ssid": "Starlink Truck", "password": "…", "joined": true },  // has worked here at least once
    { "ssid": "Back Office",    "password": "…", "hidden": true } // doesn't broadcast: probe by name
  ]
}
// which one it joins: the strongest saved network the scan hears. No priority order to manage.

// wire (edit tier unless noted)
NetworkStatus → {
  wifi, cloudRelay,
  networks: [{ ssid, hasPassword, joined, hidden? }],
  station: unsupported | off | searching                     // saved networks, none heard
         | joining { ssid } | joined { ssid, ip, rssi }
         | failed { ssid, reason: wrongPassword | notFound | noAddress }   // a code; Studio words it
}
NetworkScan → { heard: [{ ssid, rssi, secure }] }          // M6; 2.4 GHz only; hidden networks omitted
NetworkAdd { ssid, password, try: bool }                    // try=true: join first, save only if it worked; progress
                                                            //   arrives as station joining{ssid} → joined/failed + relay step
                                                            // try=false: save untested ("not here — join when in range")
                                                            // same ssid again = new password
NetworkForget { ssid }
NetworkSet { wifi?, cloudRelay? }                           // the two switches; no more ssid/password here
// M5 firmware: station=unsupported ⇒ Studio shows no scan and no test; NetworkAdd{try:true} is refused, try:false saves.
// Relay reachability (the checklist's last step) is M7's field on this reply.

6Set aside

A priority order (drag to reorder, like macOS) — the truck/house/apartment case never has two in range; “strongest wins” covers the rare overlap with no UI. A per-network on/off (#972’s “Join this network”) — forgetting is one tap and adding back is one tap from the account; a switch per network was the confusing bit. Studio ever showing a saved password — still write-only; “change password” is adding it again. Reading the computer’s current SSID — not possible from a page (top of page).
