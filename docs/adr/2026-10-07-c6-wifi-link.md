## Context

Until this change a C6 could be reached over USB and Bluetooth only. Wi-Fi
roadmap M6 puts the C6 on the house network. A board with a saved network
joins it by itself and serves the same secure lp-link the hosts already
speak, so Studio and `lp-cli` reach it as `lan:<ip>` or `lan:lp-xxxx.local`.
Everything below runs on the ESP32-C6 (`riscv32imac`, no FPU, 3 MB app
partition, ~300 KB heap). It shares the radio with ESP-NOW (the Radio
node) and Bluetooth.

## Decision

1. **The join rule.** The station joins the strongest heard network among
   the saved ones. It skips a network whose saved password was refused,
   until that password changes. A network that was just added (or
   re-keyed) is tried at once, before anything else. Saved networks have
   no order of their own.
   - The search schedule: look at once, then after 1 s and 2 s (a boot's
     first scan sometimes misses an access point that is there), then every
     10 s for the search's first minute, then every minute. A settings
     change or a lost link starts the search over.
   - DHCP retries every second, not smoltcp's 10 s, so a first DISCOVER
     lost to the WPA handshake costs a second, not the address timeout.
   - Every radio call is bounded.
2. **The Radio node rule.** ESP-NOW (the Radio node) is off while the board
   is set to use Wi-Fi. A board with nothing saved never scans, except when
   a client asks it to. The sync node that would let ESP-NOW and Wi-Fi
   share the radio is future work.
3. **LAN is first-class on the device side.** Every joined board serves the
   link on port 80 at `/link` (WebSocket). It answers mDNS for
   `lp-xxxx.local` and DNS-SD for `_lightplayer._tcp`. The cloud relay half
   is Wi-Fi M7's.
4. **Every network link is secure.** It runs lp-link's `ws()` preset with
   the secure channel (NNpsk0 keyed by the access entries). The tier comes
   from the key presented, exactly as on Bluetooth. A link whose session
   never comes up is closed at the login deadline.
5. **One LAN slot on the C6.** The plan said two, but two LAN links open
   during a project load starved the heap in the emulator. A second
   connection is told to try again later, so Studio and `lp-cli` cannot both
   be on Wi-Fi at once. A LAN link replies in JSON (a learned table would
   be 6.9 KB per link), runs a window of 2 with acks every 2 frames and a
   200 ms RTO floor (tuned for TCP: resends dropped from 36–41 to 0–1 per
   upload, emulated), and runs Nagle-off with a 2.5 KB TCP send buffer.
   The endpoint's buffers are allocated at boot when a network is saved.
6. **`lp-net`, a second thread.** The IP stack (embassy-net/smoltcp), the
   station task, the LAN endpoint and mDNS run on their own esp-rtos
   thread: 8 KB stack (high water 6,024 B on silicon), priority 1. The
   radio blobs' C heap stays in `HEAP_RADIO` (47,308 of 49,152 B on
   silicon, joined, no spill).
7. **Placement in the core.** smoltcp, the station and the LAN endpoint
   live in the core image (OTA M8's rule). A core-only board stays reachable
   over USB. Serving updates over Wi-Fi is OTA M8's.
8. **The TLS seam.** The WebSocket rides a byte stream that a TLS layer can
   later wrap. TLS itself does not fit the C6 today
   (`wifi-control-c6-measured`).
9. **Project switches on a joined board are tried and recovered**, not
   gated (`2026-10-07-project-loads-are-tried-and-recovered.md`). The 64 KiB
   load gate refused every switch with Wi-Fi joined.

## Consequences

**Measured costs** (silicon, FC6 / spare XIAO C6, 2026-10-06; emulated
figures named as such):
- **Flash:** app.bin 3,248,128 B. Gated headroom 162,128 B against the
  153,600 B floor, so 8.5 KB to spare.
- **Join:** association to address took 0.7–1.7 s on every boot of the
  re-check. The first scan missed on 4 of 19 boots (11–23 s), which is
  what the 1 s / 2 s retries are for.
- **Frame rate:** idle frame rate is −1.4 % joined, with no frame over
  100 ms. Editing cost under a synthetic load (a shader edit every ~3 s
  plus a read every 75 ms) was −56 %. That is recorded as a ceiling, not a
  target.
- **Reliability:** 0 crashes in 19 resets joined with LAN traffic. A
  10 KB transfer with three links open is refused or served, never a
  reset.

**Known limits:**
- One LAN client at a time.
- Reads on a fragmented heap are framed at half the largest block (the
  C6's block floor is 8 KiB), so a LAN link open after a switch no longer
  stops Studio reading. Yona wants the read gate itself revisited the
  try-and-recover way.
- The emulator could not join Wi-Fi until PR C's network seam.

## Amendment (2026-10-07): the one LAN slot is now the one network slot

Wi-Fi roadmap M7 (the cloud relay, PR #1019, `2026-10-06-cloud-relay.md`)
changes three of the decisions above and leaves the rest.

- **Decision 3, "the cloud relay half is Wi-Fi M7's", is now done.** A joined
  board that holds an account key and has Cloud relay on dials
  `lightplayer.app:80` itself. The relay task runs on `lp-net` beside the
  station, the LAN endpoint and mDNS, in the core, so decisions 6 and 7 hold
  for it unchanged. embassy-net's `dns` feature is on (+4,304 B), the
  stack's socket slots went 6 → 8 and its address watchers grew by one.
- **Decision 5, "one LAN slot", is now one *network* slot.** The LAN and the
  relay share the single secure session. A newcomer on the other path parks
  its first frame and is told busy unless its handshake proves the holder's
  own key, in which case it takes the slot (verification first, so a key id
  seen in the clear cannot knock a session down). Everything else in
  decision 5 (the JSON replies, window 2, the 200 ms RTO floor, Nagle off,
  the 2.5 KB TCP send buffer) is the relay link's too, because the one
  session rides either path at the same configuration.
- **"The endpoint's buffers are allocated at boot when a network is saved"
  stays for the LAN's, and does not hold for the relay's.** The relay leg's
  buffers (5,830 B) exist only while the board may dial. A first version
  allocated them at boot and took the gate case's largest block from about
  19.5 KB to 13.4 KB (emulated); see the cloud-relay ADR's "Device side".
- **Known limits.** "One LAN client at a time" now reads "one network client
  at a time, over LAN or relay". The radio blob's heap, the join rule and the
  Radio node rule are untouched.

The emulator joins Wi-Fi through PR C's network seam (#993,
`2026-10-05-emulator-seams.md` §11), and the relay's emulated uplink extends
that LAN (the same ADR's amendment of 2026-10-07).

## Amendment (2026-10-07): updates are served over Wi-Fi; the LAN link is frozen

§7's "serving updates over Wi-Fi is OTA M8's" is done (plan
`lp2025/2026-10-06-2249-ota-wifi-updates` PR A; `2026-10-06-ota-update-protocol.md`,
the amendment of this date). An engine-less, on-trial or crashing core
joins its saved network by itself and serves the update protocol on its
LAN link, answering the link's key from the device store, with no USB or
Bluetooth host. A LAN link opened in update mode advertises a window of 8
(serve mode keeps 2).

Because a fielded core that updates over Wi-Fi may be reachable only over
Wi-Fi, **the LAN link joins the frozen set** (one-way doors §6): the `ws()`
preset's masks and frames, the secure SYN and NNpsk0 handshake bytes, and
the endpoint (`ws://<board>/link`, port 80, one binary message per frame,
close 1013 when busy), pinned by `lp-base/lp-link/tests/secure_ws_bytes_golden.rs`
and `fw-esp32-common/tests/lan_endpoint_contract.rs`. A change to any of
them is a wire change for fielded cores, never a golden to re-capture.

A trial core whose boot read a saved network and on which no host link
comes up for three minutes gives the board back to its last good core
(`2026-10-04-c6-split-link-firmware-loader-and-boot-records.md`, §4's
amendment of this date), so a new core whose Wi-Fi does not work never
waits for a cable.
