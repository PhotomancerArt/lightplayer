# The S3 with Bluetooth on and a 620-pixel project running

2026-10-22. Agent-run. Emulated first; **the FS3 half ran the same evening**
(below, "On silicon: FS3"), on FS3 (XIAO ESP32-S3 Plus, 16 MB), antenna
attached.

Yona's bar, 2026-10-22: "279 KB with 200 KB at idle seems acceptable, but the
real test is once we have the radios on and a project running, especially one
at the target size of ~620 pixels." Wi‑Fi is not needed for the skirt, so
Bluetooth is the radio here.

## Verdict on silicon

**Memory fits; the frame rate is what is thin.** On FS3, with Bluetooth on and
the 620-pixel project rendering, the heap lands within 1 KB of the emulator's
figures: **62,504 B free and a 50,176 B largest free block** advertising,
**about 57.8 KB free with a central connected** (one link's 7,208 B of RAM).
The main stack peaked at **29,328 B, byte-identical to the emulator**, and the
radio region at 25,225 of 32,768 B connected, nothing overflowed. But the
board renders **16–17 fps** (a 49–61 ms render tick), advertising or
connected, with p99 ≤ 75 ms in most windows and ≤ 100 ms in the worst, and no
frame over 100 ms. The emulator's 33 fps is its untimed clock and says nothing
about this.

So, against Yona's bar: the radios and a 620-pixel project fit in RAM with
about 58 KB to spare. What fails first if the skirt wants more is **frame
rate**, not heap. Today's S3 output sends its two RMT channels one after the
other with the CPU spinning (620 LEDs ≈ 18.6 ms of wire a frame, the LED
spike's figure), which M9's LCD_CAM path removes. Whether 16–17 fps is enough
for the skirt's pattern is a product call, not a budget one.

## Verdict (emulated)

**It fits.** With Bluetooth advertising and the 620-pixel project rendering,
the main heap has **63,060 B free and a 49,524 B largest free block**, the main
stack peaked at **29,328 of 54,392 B**, the radio region at **24,517 of
32,768 B** with nothing overflowed into the main heap, and every frame on the
emulated clock came in under 33 ms. Nothing failed, nothing retried
(`retry_saves=0`).

**What runs out first** is the main heap's largest free block. It is the
thinnest margin and the one that a connection (about 7.2 KB per link on
silicon, below), a live shader edit (a second compile beside the running one)
and lane U's loader-RAM move all act on. The stack (25 KB of headroom) and the
radio region (8 KB of headroom, with overflow into the main heap allowed) are
not close.

Not yet known: silicon fps and p99 against the radio frame-rate budget, and
the heap with a central connected and editing. Both are the FS3 half.

## What ran

- **Emulator:** `lp-emu:esp32s3:t1` (the S3 machine's one time grade) at
  `ccfa116b0` (origin/main, 2026-10-22; nothing under `lp-emu/` changed on this
  branch).
- **Image:** `fw-esp32s3` at `ccfa116b0`, the shipped default features
  (`esp32s3,server,float-f32,json-pack,io-thread,heap-dram2,ble` — Bluetooth on
  by default since #1251), `just build-fw-esp32s3`, merged over
  `lp-fw/fw-esp32s3/partitions.csv` (8 MB) with `espflash save-image --merge`.
  This is the monolithic build, not the split image; both run the same engine
  and server on the same heap, and the same build is what the silicon half
  flashes (`just flash-fw-esp32s3`).
- **Boot:** ROM-up from the merged chip, so the first boot formats a blank
  `lpfs` (the tree store) and the project lives in flash, as on a board. A
  first pass by direct load had no partition table and kept the project in a
  RAM filesystem, which cost about 5 KB of heap; its figures are not used.
- **Project:** `projects/test/skirt-620` (new, this PR): two fixtures of 10
  strands × 31 lamps = **620 lamps** on two WS281x outputs (`D10`, `D9`, the
  XIAO ESP32-S3 Plus's GPIO9 and GPIO8), the way a skirt is wired down two
  sides; `projects/test/basic`'s shader (a palette-cycled noise field, four
  phasor and time inputs, 573 LPIR instructions), each fixture rendering it at
  32 × 32 and sampling Direct. It is a measurement fixture shaped like the
  real thing, not the skirt's own pattern.
- **Bluetooth:** on, advertising (`LP-Skirt 620`), no central. The emulator
  has no air: no central ever connects (AGENTS.md, "Radio is the named
  exception").
- **Host:** `lp-cli emu run --chip esp32s3 --host-link --merged <chip>
  --upload projects/test/skirt-620 --timeout 24s`, the project deployed over
  the USB lp-link exactly as `lp-cli upload` does it.

```bash
just build-fw-esp32s3
espflash save-image --chip esp32s3 --merge --partition-table lp-fw/fw-esp32s3/partitions.csv \
    --flash-size 8mb target/xtensa-esp32s3-none-elf/release-esp32s3/fw-esp32s3 merged.bin
cargo build --release -p lp-cli
target/release/lp-cli emu run --chip esp32s3 --host-link --merged merged.bin \
    --upload projects/test/skirt-620 --console console.txt --timeout 24s --wall-timeout 3500
```

24 emulated seconds took 37 minutes of wall clock on the M2 Max, beside two
other sessions' emulators. No unmapped accesses; the link carried 179 frames
out and 298 in with nothing resent or damaged.

## The figures

All emulated (`lp-emu:esp32s3:t1`, `ccfa116b0`), read from the board's own
`[MEM]`, `[stack]`, `[radio-heap]`, `[ble]`, `[mem]` and `[perf]` lines.
Memory figures transfer from the emulator; times do not (below).

### The main heap, through the boot and the load

| moment | used | free | largest free block |
|---|---:|---:|---:|
| Bluetooth up, advertising, no project (`[ble] up: controller +33400 B, host + GATT +3520 B`) | 81,600 | 196,944 | 73,736 |
| before `load_project` | 84,612 | 193,932 | 73,744 |
| after `load_project` (nodes built, nothing rendered) | 133,292 | 145,252 | 73,744 |
| first frames, before the compile finished (outputs open, render buffers allocated) | 185,060 | 93,484 | 53,244 |
| **shader compiled, rendering (steady)** | **215,484** | **63,060** | **49,524** |

The heap is 278,544 B in all (Yona's "279 KB"). The 620-pixel project costs
**130,872 B** from `load_project before` to steady: about 49 KB as the
project loads (its nodes and lamp maps), 52 KB more over the first frames
(output buffers and render textures among it), and 30 KB across the compile
(its code and what it keeps). The split between those three is read off the
moments the board printed `[MEM]`, not from an allocation trace. Its JIT code lives in the main heap on this chip (`[JIT] used=0`:
there is no separate JIT region).

|---|---:|---:|---:|---:|---:|

Render tick 28–29 ms, nothing received or sent between frames. **These are
emulated times and are evidence, never a gate**: `t1` counts one cycle per
instruction at 240 MHz and has no cache, flash or radio timing. The silicon
number is the one that counts against the radio frame-rate budget.

## Reading it against silicon

The M3 desk walk (`docs/reports/2026-10-21-s3-bluetooth-walk.md`) measured the
S3 on FS3 with Peach (1D) — 56 lamps, two shaders, 64 × 64 renders — and **two
links open**: about 200 KB used, 60 KB free, a 42,488 B largest free block,
stack high water 29,312 B, radio region 26,084 B, and **one link's RAM at
7,208 B**. From that:

- A central connected to the skirt should take the free heap from 63 KB to
  about **56 KB**, two links to about 49 KB, if a link costs the skirt what it
  cost Peach. Where the link's 7 KB lands decides the largest block.
- The radio region rose by 1.6 KB from advertising to connected on silicon;
  8 KB is there.
- Peach and the skirt land at nearly the same heap: Peach's two shaders and
  64 × 64 textures cost about what 620 lamps on one shader at 32 × 32 do. A
  skirt pattern with a second shader, or larger renders, moves this.

## On silicon: FS3

2026-10-22, 16:20–16:30. **Board:** FS3 `fixture-s3`, XIAO ESP32-S3 Plus
(16 MB), MAC `D8:3B:DA:47:29:70`, antenna attached, USB-powered, leased as
"S3 lane E". **Image:** main at `c7604ae63`, `just build-fw-esp32s3` (the
shipped default features, Bluetooth on; the monolithic build the emulator ran),
flashed with the recipe's own `espflash` arguments, and flashed again before
the lease was dropped. **Project:** `projects/test/skirt-620`, pushed over USB
with `lp-cli upload`. **Console:** `lp-cli link capture` on USB throughout.

The steady figures, the ones the bar is about, agree within 0.3 %.

### Frames

| window | fps (per 5 s window) | render tick | p99 | max | > 100 ms | > 1 s |
|---|---|---:|---|---:|---:|---:|
| advertising, no central (100 s) | 16–17 | 49–61 ms | ≤ 75 ms | 70 ms | 0 | 0 |
| connected over Bluetooth, 200 requests answered (169 s) | 15–17, median 16 | 47–68 ms | ≤ 75 ms (≤ 100 ms in 3 windows) | 81 ms | 0 | 0 |

The radio frame-rate budget (`docs/adr/2026-10-06-radio-frame-rate-budget.md`)
asks for p99 ≤ 100 ms idle and ≤ 1 s editing: both inside. Its fps ceilings
are relative to the same image with the radio off, which this sitting did not
run (owed below). Connecting costs at most a frame a second here.

**The central.** Mac Chrome 155 as the Web Bluetooth central through the
ble-lab frame pipe (`spikes/ble-lab/README.md`, "Updates over Bluetooth":
`lp-cli link capture blepipe:` with `cdp-central.mjs` answering the chooser),
not Studio: Studio's dev server could not build inside the lease with the
desk at a load average of 220. The load was `lp-cli` sending
`listLoadedProjects` and `listAvailableProjects` alternately, 200 requests,
each sent when the last was answered, all 200 answered, on one connection
(30 ms interval at connect, 15 ms once granted, ATT MTU 247; 2 frames resent
of 363). It is an active, request-carrying link like an editor's, without an
editor's writes.

## Owed

1. **Studio editing over Bluetooth**, with writes: the connected window above
   carried reads only. And the largest free block with a central connected,
   which no `[MEM]` line printed (an edit that reloads the project prints
   one).
2. **The radio-off baseline**: the same project on the default image
   without `ble`, for the fps ceiling of the radio budget.
3. **The same project on M9's LCD_CAM output**, once it is the default: the
   frame rate is where it should move.
4. **Lane U's loader-RAM move** (the S3 loader's RAM moved to the heap's edge)
   should raise the largest free block. Re-take `largest_free` when it merges;
   this report's numbers are `ccfa116b0`'s.
5. **The canonical board.** FS3 is the 16 MB Plus; the canonical S3 is the plain
   8 MB XIAO ESP32-S3. The RAM picture is the same chip's, but the walk should
   say which board it ran on.
