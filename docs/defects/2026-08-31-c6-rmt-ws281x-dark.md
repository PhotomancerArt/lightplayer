# ESP32-C6 RMT WS281x output is dark on current firmware

**Found**: 2026-08-31, device-model round-2 G1 bench (the first time a
C6 with LEDs attached met current firmware).
**Status**: root cause was never RMT at all; the symptom was TWO
independent mechanisms, one per configuration.

- **Harness half: FIXED** (PR #491, silicon-verified) — the `test_rmt`
  harness wedged in blocking USB-Serial-JTAG log writes with no reader
  on the port. Correct as written below.
- **App half: ROOT-CAUSED** (2026-09-01 evening bench) — a heap cliff at
  the compute-shader JIT compile → lp-recovery quarantines the node →
  the visual shader node renders its black fallback → the RMT driver
  transmits black frames at a healthy frame rate. The fix is tracked
  separately (see Resolution). An earlier closure of this half as a
  "BOOT-strap latch cleared by physical reset" was wrong and is
  retracted; see the app-half section for the refutation.

## Symptom

A Seeed XIAO ESP32-C6 with three known-good WS281x strips (data on
D8/D9/D10 = GPIO 19/20/18) shows NO light under current firmware, in
two independent configurations:

1. **Full app firmware** (`fw-esp32c6`, commit b16f944a1d50 on
   2026-08-31 and c3514826e056 on 2026-09-01; round 2 contains no
   output-path changes): boot log is completely healthy — `Hardware
   manifest: seeed/xiao-esp32-c6`, `Esp32C6RmtWs281xDriver: 2 WS281x
   channels for 2 declared (ch0_blocks=1 ch0_window_words=48
   ch0_half_words=24)`, `::open endpoint=ws281x:local:D10 gpio=/gpio/18
   ws281x_ch=0 rmt_slot=0 bytes=180`, engine at 43 fps, zero warnings
   in the boot sequence. Dark.
2. **`test_rmt` harness** (feature `esp32c6,test_rmt` — raw patterns,
   no pipeline, drives gpio18 directly). Dark.

**Known-good reference**: the SAME board + SAME strips animated
earlier the same day under its previous firmware (wire proto 12,
current 2026-08-05 → 2026-08-09 per the `WIRE_PROTO_VERSION` bump
history in `lp-core/lpc-wire/src/server/hello.rs`).

## Why this went unseen

Every recent C6 bench walk (round-1 G1 included) used boards with no
LEDs attached; the classic V3/dome path (separate driver) kept
working. The regression window is proto-12 era → now.

## Suspects (code-read before bisecting; each touched this ground)

- The RMT block-plan rework (`fw-esp32c6/Cargo.toml` notes "the former
  `ws281x_2blocks` feature is gone: the RMT block plan is now …").
- esp-hal upgrades across the window (RMT + clock APIs; the boot line
  says "Initializing RMT peripheral at 80MHz…" — a clock/divider
  change would silently wreck bit timing while logging success).
- Packed display layouts (proto 18) — full-fw path only; the harness
  being dark too argues BELOW the pipeline.
- io_task/serial rework (#448) — unlikely (harness has no serial load).

None of these was the cause, in either configuration.

## Verification tools

`ws281x_telemetry` feature (counters), `test_rmt` harness,
`fixture-fw`-style build+flash (BUILD FROM THE CRATE DIR — a
workspace-root cargo build misses the linker script), espflash CLI,
human eyes on the bench (no logic analyzer on hand), and — the one
that actually cracked the app half — the device's serial journal read
end to end, not just its boot sequence.

## Root cause, harness half (2026-08-31)

Not RMT, not timing, not the block plan. Code archaeology first: between
the proto-12-era known-good build (proto 12 was current 2026-08-05 →
2026-08-09, dated via the `WIRE_PROTO_VERSION` history — "months-old" in
the symptom was wrong) and HEAD, there are **zero changes** to
`lp-ws281x`, the C6 RMT backend, the harness, the timing constants,
esp-hal (1.1.1 at both ends), or the build/toolchain config. The
known-good firmware already ran today's exact driver code, so every
suspect above was exonerated before touching hardware.

The real mechanism, reproduced twice on the bench: **the harness wedges
in its own startup logging when no host is reading the USB-Serial-JTAG
port.** esp-hal 1.1.1's blocking `UsbSerialJtag::write` spins after
each ≤64-byte chunk until the USB host drains the EP1 buffer
(`usb_serial_jtag.rs:183`, `while ep1_conf & 0b011 == 0b000`). Output
over USB-Serial-JTAG only leaves the chip when something reads the
port; espflash closes the port after `--after hard-reset`, so `test_rmt`
blocked at its first `info!` — before its first LED frame — and sat
there indefinitely. The moment *any* process opened the port (even a
bare `cat`), the buffer drained, the write returned, and the chase
pattern started. That was the observed "un-sticking."

The dark→lit transitions on the bench mapped 1:1 to port opens, never
to reset flavor: flash + hard-reset with the port untouched → dark;
open the port, no reset → chase starts within a second; bare
`espflash reset` untouched → dark again.

The **full app firmware is immune to this mechanism**: it installs
`logger::init(io_task::log_write_to_outgoing)`, which rides io_task's
`ChunkedWriter` (`WritePolicy::USB_SERIAL_JTAG`: 250 ms chunk timeout,
not-draining latch, probe writes) — machinery built when this exact
USB-drain behavior was first met early in development. Only the
harnesses bind the logger straight to the blocking
`Esp32UsbSerialIo::write`, which predates that machinery.

## Root cause, app half (2026-09-01, bench)

The app-dark observation was real and is a **second, independent
mechanism** — and it is not electrical, not RMT, and not a reset
artifact. It is a heap cliff, quarantined into silence.

**Refutation of the BOOT-strap-latch story.** The 2026-09-01 morning
closure claimed that on USB-JTAG chips a software reset after download
mode leaves the BOOT strap latched, so the app boots healthy but
produces dead output until a physical reset. The evening bench refuted
that outright: LEDs dark, and **no reset helps** — software reset,
the physical reset button, and a power-on replug all boot into the
same dark state. A strap latch cannot survive a power cycle. The theory
came from a single observation (physical reset → meteor lit) that has a
different explanation, below.

**The mechanism**, from the serial journal of the same board on the
same firmware (c3514826e056, Meteor example):

```
allocation failed: requested=252 align=4 free=128 used=299872 context=compute shader node: compile
[RECOVERY] last run crashed (oom): at node:/studio.show/o/…/node:/studio.show/s
[WARN] [visual-shader-node] bound inputs failed to resolve: input using its default: produce: tick failed: recovery: node '/studio.show/s' (disabled after 3 crashes)
[WARN] [shader-node] sampling black fallback (frame 1): shader not compiled
```

1. **Heap cliff.** Meteor on the C6 (esp_alloc heap of 300_000 B,
   `lp-fw/fw-esp32c6/src/board/esp32c6/init.rs:31`) is ~250 B over the
   heap at the compute-shader JIT compile (`requested=252`,
   `free=128`). On this chip an allocation failure is fatal: the board
   crashes and reboots.
2. **Recovery quarantine.** lp-recovery's ledger records the crash
   against the node path; a second crash on a path already under watch
   gates it RED (`lp-base/lp-recovery/src/ledger.rs` ~:142). From then
   on the node is refused at tick time — `disabled after N crashes` —
   so the shader is never compiled.
3. **Black fallback.** The visual shader node's bound input fails to
   resolve and falls back to its default; the shader node samples its
   black fallback texture (`shader not compiled`). The engine keeps
   running at 43 fps, the RMT driver is genuinely open on gpio18
   (`bytes=180`), and it transmits black frames — `FRAME_TIMEOUT`
   (50 ms) is never hit. Every health signal in the boot log is
   truthful. The output is black by construction.

**Why it is deterministic across every reset flavor.** A power-on
clears the RTC ledger, but the OOM recurs on the very next boot, so the
quarantine re-arms within two boots (observed: `disabled after 2
crashes` at 19:27:47, `disabled after 3` at 19:28:05). The steady state
after any reset is the same dark board.

**Why one physical reset "worked" on 2026-08-31.** The previous day's
build b16f944a1 sat ~250 B on the *fitting* side of the cliff. A reset
gave it a boot whose compile fit, the meteor lit, and the full
first-plug loop ran — which read as "physical reset clears the strap."
The 2026-09-01 build c3514826e (wedge fix + build noise) never fits.
The illusion was that reset flavor mattered; the variable was build
size against the heap. The same OOM → recovery pairs are already in
the 2026-08-31 journal at 14:23, 16:05 and 16:08 — the dark walk was
logging its own root cause all day.

**Why the studio could not show it.** The device card kept saying
"Running": lpa-devices' heartbeat mirror keeps only identity + loaded
and drops `RecoveryStatus` (level, last crash), so a recovery-disabled
node is invisible from the card.

**Precedent**: `2026-08-01-classic-rmt-open-fault.md` — the same
misattribution shape on the classic (an "RMT open fault" that was heap
exhaustion), and the same silent-black outcome. See also
`2026-08-29-shader-jit-compile-transient-starves-classic-heap.md` for
the compile transient's size on the classic.

## Resolution

**Harness half (fixed, PR #491).** `Esp32UsbSerialIo::write` (fw-esp32c6
and the fw-esp32s3 twin) now performs bounded, best-effort writes:
`write_byte_nb` under a 250 ms deadline (mirroring
`WritePolicy::USB_SERIAL_JTAG`), a `host_draining` latch so later writes
fast-drop via a single probe byte instead of re-paying the deadline, and
a fire-and-forget `flush_tx_nb` for partial chunks. Silicon-verified
both ways on the bench board: flash → hard-reset → port untouched →
chase runs unattended; reset with a reader attached → all startup log
lines delivered, then chase.

**App half (fixed across two PRs, 2026-09-02).** Three items, each its own
change:

1. **Heap headroom for the flagship example on the C6.** FIXED on main by PR #495: the OOM was `lps-glsl` HIR place clones, not heap marginality, and the C6 RAM was re-split (72 KB main stack, heap +64 KB from dram2) — see `docs/adr/2026-09-02-esp32c6-ram-split.md`. The original candidates: Meteor must
   fit with margin, not by ~250 B either way. Candidates: measure the
   compile-arena peak; shrink Meteor's residents (residents-eat-the-heap
   lore, #471 probes); enlarge the allocator if RAM allows.
2. **"A fault is never black" output pattern.** FIXED by PR #496 (`docs/adr/2026-09-02-fault-is-never-black.md`; defect `2026-09-01-silent-black-under-node-quarantine.md`): a new `NodeRuntimeStatus::Fault` level and a red breathe on every output of a faulted project. A recovery-disabled
   node, an uncompiled shader, or an unresolved bound input must not
   render as the same black the user would see from a dead wire. A
   degraded node needs a visibly-not-black output convention.
3. **Card surfaces `RecoveryStatus`.** FIXED by PR #496: the mirror keeps recovery + the project fault, the card reads Degraded, and a Clear faults verb clears the ledger (wire 20). The heartbeat mirror must carry
   recovery level + last crash so the device card reads "degraded: node
   … disabled after N crashes (OOM at shader compile)" instead of
   "Running", with a way to clear the ledger (the Reset verb is not
   enough; power-on clears but re-arms).

The round-2 M4 "programmatic true-reset ladder rung" that the retracted
closure proposed is DROPPED — there is no reset mechanism to fix.

## Regression coverage

None yet for the app half: the failure lives at the intersection of a
real device's heap and a real example's compile transient. Item 1 above
should land with a measured headroom number for Meteor on the C6; item
3 with a heartbeat/card test that a RED ledger entry is displayed.

## The lesson

A harness that logs before its first unit of real work has a boot
dependency on its *observer*: over USB-CDC transports, "prints logs"
requires a reader, so an unattended harness must treat log writes as
droppable or it turns into a hardware-shaped deadlock. The symptom is
maximally misleading — the subsystem under test looks broken while the
actual wedge is in the instrumentation — and it recruited every
plausible suspect (esp-hal upgrades, block-plan rework, bit timing)
because "dark LEDs" reads as an output-path failure. When a "regression"
window contains zero changes to the implicated code, believe the diff:
re-examine the observation before the theory.

**"Engine fps healthy + driver open + dark" means black frames, not a
dead wire.** Before any electrical or reset theory, grep the device
journal for `black fallback` and `disabled after` — a quarantined node
and a fault-default input produce exactly this signature, with every
boot-time health line truthful. The 2026-08-31 journal contained the
answer three times while the bench chased RMT, straps, and reset
flavors; the failure was in reading only the boot sequence. This is
the second time on this project that "RMT is dark/faulting" was heap
exhaustion (`2026-08-01-classic-rmt-open-fault.md`); treat it as the
default hypothesis for silent black on a device.

And: one symptom, two mechanisms. The harness and app configurations
were dark for unrelated reasons (logger wedge vs heap-cliff
quarantine), and the shared symptom made each half look like
confirmation of the other — "the harness is dark too" was read as proof
the bug sat below the pipeline. Closing the first mechanism found does
not close the symptom; each observed configuration owes its own re-run.
And a closure built on a single un-reproduced observation (one reset,
one lit meteor) is a theory, not a root cause: the BOOT-strap story
lasted until the first attempt to repeat it.
